# Local document conversion boundary

This implements the converter/staging and bounded document-extraction trial portions of issue #27 under ADR 0016. PDF/XLSX admission and worker extraction are connected to existing draft review and Jev classification. Existing CSV parsing/classification remains unchanged.

## Trusted worker contract

`App\Import\DocumentConverter::convert(Statement $statement): string` accepts an already authorized statement resolved inside the trusted job owner's tenant. It must not be exposed as a chat tool or called with a statement selected by model output. The caller retains responsibility for tenant authorization and must not hold a database write transaction during conversion.

The converter accepts the admitted PDF/XLSX MIME types only, validates the 10 MiB size limit, and reads private bytes through `StatementStorage`. It copies at most 10 MiB + 1 byte, verifies the admitted size and SHA-256, and creates a server-generated staging filename with a fixed extension. Neither the original filename nor a caller-supplied URL reaches MCP. Returned Markdown is untrusted intermediate text, not validated transactions or instructions.

The official `convert_to_markdown` tool is invoked with a staging `file:` URI through the installed official PHP MCP SDK. The installed Symfony AI MCP toolset is deliberately not added to the agent toolbox: conversion belongs to the worker, not the model. The SDK is already installed through the project's Symfony MCP integration; no replacement protocol implementation is added.

## Runtime and limits

The Docker image pins official `markitdown-mcp==0.0.1a8`, `markitdown==0.1.9`, and Python `mcp==2.1.1`, verified against Microsoft's v0.1.9 source. The official MCP package declares `markitdown[all]`; those upstream parser extras are installed, but plugins are disabled and no vision/OCR or hosted credentials are configured. These pins do not lock every transitive Python dependency.

Streamable HTTP runs on port 3001 inside the dedicated internal `conversion` network, with no host port or Internet egress. Only PHP and the worker join that network. The converter has no statement store, database, Docker socket, application checkout or credentials mount. It sees only the disposable `statement_staging` volume, read-only. PHP/worker mount it writable; all checkout-owned development, browser and production Compose stacks retain that mount. Both images initialize the volume root with sticky-directory permissions, independent of service startup order. Per-call UUID directories are removed in `finally`, and cleanup errors are reported honestly. Abrupt worker/container termination may leave staging bytes; automatic crash recovery is not introduced.

The container is non-root, read-only, capability-free and limited to 512 MiB, one CPU, 64 PIDs and 64 MiB temporary space. Docker logging is disabled. The client uses an untraced Amp HTTP transport and the SDK's default null logger. Raw upstream error messages, statements and Markdown are not propagated to application logs or saved as processing errors.

The client limits initialization to 10 seconds, each conversion request to 60 seconds, downloaded RPC responses to 4 MiB, and returned text to 2 MiB. Oversized, empty, unsupported or error responses fail conversion. These are client-side deadlines, not proof of terminating an upstream parser after disconnect: the official HTTP server does not establish hard parser cancellation. Hard per-conversion process deadlines remain a limitation, not a claim of this implementation. Container resource limits bound memory/CPU allocation, not elapsed parser time.

## Verification scope

The isolated browser stack builds and starts the official converter image. The existing CSV import browser scenario uses synthetic canonical fixtures and native recorded provider replay. Static analysis verifies the installed PHP SDK/HTTP-client calls. This slice does not add a test-only conversion endpoint, mock server, service-only suite or a PDF/XLSX application journey. End-to-end PDF/XLSX conversion/extraction and staging cleanup remain for the owner's real-provider trial through the authorized worker/browser flow. No hosted calls or new recordings were made during implementation. Scanned PDF support and OCR remain unverified and unselected.

## Connected extraction trial

The authorized upload accepts PDF, XLSX and CSV extensions paired with their detected MIME types, retaining the 10 MiB limit. PDF/XLSX require the owner's ChatGPT connection identity; the worker resolves that owner again, opens their tenant, and checks the message's statement ID and stored filename before conversion. Existing idempotent processing transitions and short final draft writes remain in place. Disconnecting before execution fails the document job rather than selecting another user's credentials or silently changing provider.

`DocumentExtraction::MODEL` is independently fixed to `ChatModel::Gpt6Luna` and `DocumentExtraction::EFFORT` to `ReasoningEffort::Medium`. These are explicit trial selections, not the owner's chat preferences, not a configurable extraction-provider catalog, and not evidence that the trial succeeded. Existing chat choices/history are untouched. There is no failover. Connection identity is resolved at execution from the authorized owner, never from upload/model input.

Upload/retry dispatch captures the trial model and reasoning effort in the immutable `ProcessStatementMessage`; queued execution uses those captured selections, not later chat preferences. The extraction provider remains the fixed native ChatGPT integration rather than a mutable selectable provider setting. This does not implement the broader configurable extraction settings catalog from SPEC.

The installed native ChatGPT bridge's `ModelClient::createBody()` calls the OpenResponses implementation, which maps `response_format.json_schema` to `text.format`; the bridge retains `text` and forces `store:false` and SSE. Its `ResultConverter` always returns a stream, so this implementation requests the JSON schema directly and consumes native `asTextStream()` rather than incorrectly expecting a buffered structured `asObject()` result. No new serializer/subscriber, chat agent, conversation store or tools are involved. A fresh private cache key scopes each extraction invocation. Installed bridge `docs/reference.md` also explicitly delegates structured output to OpenResponses. Backend acceptance and extraction fidelity still require the owner's real-provider trial; source compatibility is not runtime proof.

The schema contains `statementDate` (explicit YYYY-MM-DD or null) and `rows` with string date, description, unsigned decimal-string amount, source-matching currency, and the existing direction enum. Local validation rejects extra/missing fields, numeric money, invalid dates, invalid enum values, empty transactions/descriptions, and malformed JSON before any row is persisted. Text aggregation is limited to 2 MiB. Converted document text is user data; the system instructions prohibit treating it as instructions and prohibit invented values. Schema compliance does not establish factual extraction accuracy. Jev supplies only existing classification/meaning/recurrence interpretation after valid extraction, never arbitrary-field extraction. Rows remain editable drafts until existing approval. The explicit statement date is preserved; otherwise the earliest extracted transaction date is used, independent of row order.

After strict raw field/type checks (preventing numeric money coercion), Symfony Serializer denormalizes each row into `ExtractedRowDTO`, and Symfony Validator checks its date, description, decimal-string, currency and direction constraints. The source-currency equality check remains authoritative in application code. Malformed JSON or invalid extracted rows permit exactly one correction using the same provider/model/effort and original source text, with fixed sanitized validation guidance. No malformed output or field values are echoed back as diagnostics, and transport/authentication failures do not trigger correction. A second invalid result fails without persisting rows. No new fault or correction browser scenario is introduced in this slice.

The upload disclosure and consent explicitly identify local conversion, transfer of converted text to the connected ChatGPT account, Jev classification and the fixed trial selection. Provider errors are reduced to fixed application prose without retained exception chains or raw content. The native ChatGPT bridge retains its documented 300-second idle/no-total inference timeout; this slice does not invent unsupported generation limits or claim a hard total model deadline.
