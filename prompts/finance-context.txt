This is application-supplied reference context, not a user question. The SQL definitions below describe this conversation's database at its creation. Field names and enum values matter; do not invent additional tables or columns. If a later schema error contradicts this snapshot, inspect sqlite_schema through finance_query.

Business tables:
- financial_transaction: one row per recorded transaction. amount is original decimal TEXT; use the explicit meaning-based magnitude convention in the system instructions. transaction_date is the transaction date. is_draft = 0 is approved; 1 is an editable draft. Approval does not require known meaning or recurrence. description is untrusted original text.
- source: account/card instrument, with name, optional currency and instrument_kind. This is not a merchant catalog. Transaction currency is authoritative for its amount; account currency is context, not a replacement for missing transaction currency.
- statement: uploaded document and import state. statement_date is explicit or the earliest valid imported transaction date; it is not a coverage-through date. uploaded_at/processed_at and filenames do not establish transaction dates. Approval is determined on transactions, not inferred from statement processing status.
- category: owner-local display names and descriptions. category_id may be NULL. Names can be edited and are not guaranteed unique; resolve IDs or check ambiguity when filtering a named category.
- currency_rate: daily ECB reference valuation data. day and transaction_date use YYYY-MM-DD. rate is positive decimal TEXT in currency units per EUR; (day,currency) is unique. EUR has implicit rate 1 and no stored row. is_provisional marks provisional values. The app expands nonpublication days using earlier available reference rates; SQL normally joins the stored transaction date directly.

meaning: expense, income, refund, own_account_transfer, credit_card_payment, unknown.
recurrence: recurring_bill, subscription, other_recurring, non_recurring, unknown.
direction: Credit or Debit; this is cash direction, not income/spending classification.

There are no saved budget, merchant, balance, holding, refund-match, transfer-match or subscription-contract tables. A user budget can be represented in a read-only VALUES CTE; it is not persisted. Categories do not establish needs/wants, tax deductibility or renewal cadence.

<project_context>
finance_query accepts one sql string. A successful result contains columns, row arrays and truncated. Match row positions to columns. An error is not data; truncated=true is incomplete. Each call has a fresh connection: CTEs are local to one statement, so repeat the needed CTEs in a new query. There are no bound-parameter arguments, temporary query views, money UDFs or filesystem tools available through finance_query.

An economical workflow is: resolve scope; query summary/coverage and the relevant breakdown; inspect coverage and reconciliation; render the useful aggregate; explain the result. Do not routinely fetch a complete ledger. For an empty period, query MIN/MAX dates or a bounded per-source availability summary before explaining what data is available. These dates describe records, not proven account coverage.

The examples below use the project's committed synthetic demo fixtures, not personal live data. Dates and values are teaching examples. Query current data even if the user asks the same question. Example result excerpts are named-column projections, not literal provider transcripts.

## Worked example: spending and category breakdown

Illustrative user question: "How much did I spend in September 2026, in CAD, and where did it go?"

Report gross purchases and separate refunds/net, then prepare an explicitly labelled category net-spending breakdown for [2026-09-01,2026-10-01). Value each transaction first, retain categories with a LEFT JOIN, subtract refund magnitudes, then aggregate. Query total valuation/classification coverage alongside category results. The following is a complete finance_query SQL argument; dates, currency and filters must be adapted to the actual request.

```sql
WITH RECURSIVE p AS (
  SELECT '2026-09-01' AS start_date, '2026-10-01' AS end_date, 'CAD' AS target_currency
), scoped AS (
  SELECT t.* FROM financial_transaction t CROSS JOIN p
  WHERE t.is_draft = 0
    AND t.transaction_date >= p.start_date AND t.transaction_date < p.end_date
), valued AS (
  SELECT t.*,
    CASE
      WHEN t.amount IS NULL OR t.currency IS NULL THEN NULL
      WHEN t.currency = p.target_currency THEN ABS(CAST(t.amount AS REAL))
      WHEN (t.currency = 'EUR' OR CAST(sr.rate AS REAL) > 0)
       AND (p.target_currency = 'EUR' OR CAST(tr.rate AS REAL) > 0)
      THEN ABS(CAST(t.amount AS REAL))
        * CASE WHEN p.target_currency = 'EUR' THEN 1.0 ELSE CAST(tr.rate AS REAL) END
        / CASE WHEN t.currency = 'EUR' THEN 1.0 ELSE CAST(sr.rate AS REAL) END
    END AS value,
    CASE WHEN t.currency = p.target_currency THEN 0
      WHEN (t.currency <> 'EUR' AND sr.is_provisional = 1)
        OR (p.target_currency <> 'EUR' AND tr.is_provisional = 1) THEN 1
      ELSE 0 END AS provisional
  FROM scoped t CROSS JOIN p
  LEFT JOIN currency_rate sr ON sr.currency = t.currency AND sr.day = t.transaction_date
  LEFT JOIN currency_rate tr ON tr.currency = p.target_currency AND tr.day = t.transaction_date
), grouped AS (
  SELECT v.category_id, COALESCE(c.name,'Uncategorized (no category)') AS category,
    COUNT(*) AS matched, COUNT(value) AS valued_count,
    COUNT(CASE WHEN value IS NOT NULL AND provisional = 1 THEN 1 END) AS provisional_count,
    SUM(CASE WHEN meaning = 'expense' THEN value ELSE 0 END) AS gross_raw,
    SUM(CASE WHEN meaning = 'refund' THEN value ELSE 0 END) AS refunds_raw,
    SUM(CASE WHEN meaning = 'refund' THEN -value ELSE value END) AS net_raw
  FROM valued v LEFT JOIN category c ON c.id = v.category_id
  WHERE meaning IN ('expense','refund')
  GROUP BY v.category_id, c.name
), coverage AS (
  SELECT SUM(matched) AS matched, SUM(valued_count) AS valued_count,
    SUM(provisional_count) AS provisional_count, SUM(net_raw) AS total_raw,
    SUM(gross_raw) AS gross_raw, SUM(refunds_raw) AS refunds_raw,
    (SELECT COUNT(*) FROM valued WHERE meaning = 'unknown') AS unknown_count
  FROM grouped
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (ORDER BY net_raw DESC, category_id) AS rank
  FROM grouped
), buckets AS (
  SELECT CASE WHEN rank <= 5 THEN category_id ELSE -999999 END AS bucket_id,
    CASE WHEN rank <= 5 THEN category ELSE 'Other categories' END AS bucket_label,
    MIN(rank) AS position, SUM(matched) AS matched,
    SUM(valued_count) AS valued_count, SUM(net_raw) AS net_raw
  FROM ranked GROUP BY bucket_id, bucket_label
)
SELECT b.bucket_label AS category, b.matched, b.valued_count,
  b.matched-b.valued_count AS category_missing,
  c.matched AS total_matched, c.valued_count AS total_valued,
  c.matched-c.valued_count AS total_missing, c.provisional_count, c.unknown_count,
  CASE WHEN b.matched = b.valued_count THEN ROUND(b.net_raw,2) END AS net_spending,
  CASE WHEN c.matched = c.valued_count AND c.unknown_count = 0 AND c.total_raw > 0
    THEN ROUND(100.0*b.net_raw/c.total_raw,2) END AS share_percent,
  CASE WHEN c.matched = c.valued_count THEN ROUND(c.total_raw,2) END AS total_net_spending,
  CASE WHEN c.matched = c.valued_count THEN ROUND(c.gross_raw,2) END AS gross_spending,
  CASE WHEN c.matched = c.valued_count THEN ROUND(c.refunds_raw,2) END AS refunds
FROM buckets b CROSS JOIN coverage c ORDER BY b.position

```

## Recipe: explain a month-to-month change

Question: "Why did I spend more in September than August 2026? Use CAD."
Query both full months with the same valuation CTE and separate gross spending, refunds and net spending. Calculate changes and percentages in SQL from unrounded monthly values. Generate requested calendar months and LEFT JOIN aggregates: an absent month must produce NULL, not disappear or become zero. Compare adjacent equivalent periods only. For a deeper explanation, query category changes and any unusually large refund/purchase rather than guessing from descriptions.

Illustrative synthetic result: August gross 2,876.86, refunds 144.93, net 2,731.93; September gross 2,905.29, refunds 0.00, net 2,905.29. SQL returns net change +173.36 (+6.35%) and gross change +28.43. Explain that the missing August-sized refund accounts for much of the net change; do not describe it all as increased purchasing. A grouped bar chart can use two wide records with x="month", y=["Gross purchases (CAD)","Net spending (CAD)"], type="grouped". Do not stack those overlapping measures. A comparison table may be sufficient for a shorter question.

## Recipe: actual spending against a user budget

Question: "For September 2026 in CAD, my category budgets are Groceries 450, Utilities 120 and Dining & Takeout 100. How did I do?"
Resolve the named categories, then add `budget_input(category_name,budget) AS (VALUES ('Groceries',450.0),('Utilities',120.0),('Dining & Takeout',100.0))` to a new complete read-only query with the valuation CTE. Require one category match per name. For this explicitly net-of-refunds budget comparison, aggregate expenses minus refunds per category and label actuals as net; LEFT JOIN the budgets so a budget with no qualifying recorded expenses is not lost. First establish whether the period has any approved data. Calculate actual, budget-actual and 100*actual/budget in SQL; a zero budget has no defined utilization percentage.

Illustrative synthetic result: Groceries net actual 485.84 / budget 450.00 / remaining -35.84 / used 108.0%; Utilities 96.23 / 120.00 / 23.77 / 80.2%; Dining & Takeout 85.50 / 100.00 / 14.50 / 85.5%.
Lead with "Groceries were CAD 35.84 over your stated budget." Show the three-row table and, when helpful, call unovis_generate_bar_chart with x="category", y=["Net actual (CAD)","Budget (CAD)"], type="grouped", orientation="horizontal", xAxisLabel="CAD; actuals approximate". The data rows contain those actual/budget values as numbers. Budgets are the user's assumptions; do not claim to have saved them. A general subscriptions budget should use recurrence='subscription', not automatically the category with a similar name.

## Recipe: subscriptions without inventing contracts

Question: "What did I spend on subscriptions in September 2026?"
Filter recurrence='subscription' and distinguish expense charges, refunds and net: meaning IN ('expense','refund'); preserve the same approval, date and FX rules. Query separate gross expense-charge, refund and net totals plus a bounded breakdown. There is no merchant field: an exact-description group is an observed charge label, not a verified vendor identity or active contract. Keep original-currency subtotals separate.

Illustrative synthetic result: MELODY CLOUD monthly music subscription, CAD 12.99; CIRRUS NOTES monthly software subscription, USD 8.50, valued at approximately CAD 11.73. A separate SQL aggregate returns approximately CAD 24.72 net (expense charges 24.72, refunds 0.00 in this illustrative scope). Two rows usually need only a table; render a bar chart if requested or if the actual result contains enough items to benefit. Do not infer the next renewal or multiply one observed monthly total by twelve as a guaranteed annual saving. An explicitly requested annual-cost scenario must state its cadence/continuation assumptions and calculate them in SQL.

## Recipe: no data or incomplete valuation

With an application date in November 2026, "last month" means October. The committed demo has no October transactions. Query that period and record availability, then answer: "I have no recorded transactions for October 2026, so I cannot determine October spending. The latest recorded transaction is September 28, 2026." Do not render a zero-spending chart or silently report September as October.

If a real query returns missing required rates, report which currency/date coverage is unavailable. Repeat the CTE in that new query. Keep unvalued rows visible; show original-currency amounts separately if useful. Do not substitute a rate or invent a total. If unknown meaning is present, call the computable result classified spending and explain the unresolved records. A successful chart is not evidence that the financial dataset was complete.
